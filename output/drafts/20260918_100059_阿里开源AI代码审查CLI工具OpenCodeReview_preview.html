阿里把代码审查的AI塞进了终端，token只要通用方案的九分之一

每天早上打开 GitHub，二十几个 PR 排队等你 review。那感觉比周一早高峰挤地铁还窒息。

你点开第一个，扫两眼，留一句“这里边界没处理”，翻到下一个。到第五个的时候，眼睛已经开始自动跳过代码，只看文件名和 commit message 了。这不是懒，是人脑在高频重复判断中必然出现的精度衰减。

代码审查这件事，本质上是个规模不经济的活儿。团队越大，PR 越多，每个 PR 分到的注意力越少，漏网之鱼就越多。

所以过去一年多，几乎所有人都在往这个环节塞 AI。让模型去读 diff，自动留评论，听起来很美。真用起来你会发现两个问题，一个比一个疼。

第一个是精度。通用 Agent 看代码，经常抓错重点。它会在你改了一个变量名的地方长篇大论命名规范，却对旁边那个真正的并发隐患视而不见。F1 分数上不去，开发者被误报训练成“看到 AI 评论就点 resolve”，工具形同虚设。

第二个是成本。一个中等规模的仓库，每天几十个 PR，每个 PR 让通用 Agent 全量扫一遍，token 消耗跟流水一样。有团队算过账，光是 AI review 这一项，一个月烧掉的 API 费用够养一个初级工程师。

这两个问题不解决，AI 代码审查就永远停在 demo 阶段，进不了生产流水线。

阿里这次做的事情，值得认真看一眼。

他们把内部用了很久的 AI 代码审查助手开源了，做成了一个 CLI 工具，叫 OpenCodeReview。你可以在终端里直接跑，不需要打开浏览器，不需要 IDE 插件，一条命令下去，它自己拉 diff、分析、输出评论。

但真正有意思的不是形态，是架构。

这个工具没有走“一个大模型包打天下”的路子。它把整个审查流程拆成了两层，确定性工程层和 LLM Agent 层。

确定性那层干什么？文件选择、规则匹配、评论定位，全是确定性逻辑。哪些文件改动值得看，哪些规则适用，评论该挂在第几行，这些事情不需要模型来判断。用代码写死的逻辑去做，又快又准，而且零 token 消耗。

Agent 那层只负责一件事，动态决策。遇到需要理解上下文、判断意图、权衡轻重的地方，才交给模型。模型不需要处理那些机械环节，只处理真正需要“脑子”的部分。

这个拆分带来的结果很直接。精度上，F1 比通用 Agent 更高。为什么？因为确定性逻辑把脏活累活干了，模型不用在噪音里找信号，专注在真正需要判断的地方，误报和漏报都降下来了。

成本上，token 消耗只有通用 Agent 的九分之一左右。这个数字不是随便说说的。通用 Agent 做代码审查，大量的 token 花在读文件、理解目录结构、反复确认位置这些机械动作上。OpenCodeReview 把这些全部前置到确定性层，模型只处理最后那一小段需要推理的内容，token 自然就下来了。

九分之一是什么概念？原来一个月烧一万块的团队，现在一千出头。原来不敢对每个 PR 都跑 AI 的团队，现在可以全量覆盖。成本结构变了，用法就变了。

我特别想说的是，这个工具的设计思路，比工具本身更有价值。

过去两年，行业里有一种很偷懒的思维，遇到问题就想着“上大模型”。代码审查效果不好？换个更大的模型。成本太高？等模型降价。这种思路的问题在于，它默认模型应该解决所有问题，包括那些根本不需要智能的问题。

OpenCodeReview 走的是另一条路。先把问题拆开，哪些是确定性的，哪些是需要智能的。确定性的用工程解决，智能的用模型解决。 模型不是万能的，它只该出现在真正需要它的地方。

这个思路其实更接近人类团队的工作方式。一个资深的 reviewer，不会从头到尾逐行读代码。他先扫一遍改动范围，判断哪些文件是核心逻辑，哪些是配置文件不用细看。然后针对核心改动，结合上下文做判断。前面那步是确定性的，后面那步才需要经验。

OpenCodeReview 把这两步分开了，用代码做第一步，用模型做第二步。

对于每天要过大量 PR 的团队来说，这个东西最大的价值是它能直接塞进 CI 流程。你不需要改变任何现有工作流，在 CI 里加一行命令，每个 PR 提交后自动跑一遍，评论直接留在 diff 上。开发者看到的反馈是精准的、有上下文的，不是那种“这个函数太长了”的废话。

有人可能会问，阿里内部用得好，开源出来就一定好用吗？

这个问题得反过来看。阿里内部代码仓库的规模、PR 的吞吐量、代码规范的复杂度，都远超一般团队。内部能跑通的东西，开源出来至少下限是有保证的。而且 CLI 工具的形态决定了它不挑技术栈，不挑托管平台，你用的是 GitHub、GitLab 还是自建的 Gerrit，都能接。

当然，它也不是没有局限。确定性规则那层需要你根据自己的代码规范去配置，不是开箱即用。Agent 那层对模型能力有要求，便宜的模型效果会打折扣。但这些都是工程问题，不是方向问题。

方向对了，剩下的就是调优。

代码审查这件事，说到底是在做注意力的分配。人的注意力有限，应该花在真正需要判断的地方。AI 的 token 也有限，应该花在真正需要智能的地方。OpenCodeReview 做的事，就是让两边都不浪费。

那些还在用通用 Agent 硬扫代码的团队，值得花一个下午试试这个工具。不是为了省那点 token 钱，是为了让 AI 评论真正被开发者当回事。

从实践中来，到系统中去。
